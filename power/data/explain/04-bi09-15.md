@@lesson bi9
@image
**FILTER** は「表を1行ずつ見て、条件に合う行だけを残した表を作る」関数です。パワークエリの行のフィルターに似ていますが、DAX では **メジャーの中で、その場で** 行を選びます。

CALCULATE の条件には「列 = 値」のような単純な条件しか書けませんでした。**「売上が5万円以上の商品」のように、計算結果（メジャー）を条件にしたい** ときに FILTER の出番です。

@detail
### 1. FILTER は「表」を返す
```dax
FILTER(売上, 売上[金額] >= 5000)
```
売上テーブルを1行ずつ見て、金額が5000以上の行だけの表を返します。表なので、そのままでは数値として表示できません。**COUNTROWS で数える**、**CALCULATE の条件に渡す** などして使います。
```dax
大口注文件数 = COUNTROWS(FILTER(売上, 売上[金額] >= 5000))
```
| カテゴリ | 2025 | 2026 |
|---|---|---|
| ドリンク | 12 | 6 |
| 菓子 | 5 | 4 |
（文具・雑貨は5000以上の注文がないので、行ごと表示されない）

### 2. メジャーを条件にしたい
「売上金額が5万円以上の商品の数」を数えたい。CALCULATE の条件に `[売上金額] >= 50000` は書けません。そこで：
```dax
売れ筋商品数 = COUNTROWS(FILTER(VALUES(商品[商品名]), [売上金額] >= 50000))
```
| 部分 | 意味 |
|---|---|
| `VALUES(商品[商品名])` | 今見えている商品名の一覧（ドリンクの行ならドリンクの商品だけ） |
| `FILTER(…, [売上金額] >= 50000)` | その一覧を1つずつ見て、売上5万以上の商品だけ残す |
| `COUNTROWS(…)` | 残った商品の数 |

ドリンクの行で何が起きるか：
| 商品名 | その商品の売上 | 残る？ |
|---|---|---|
| コーヒー豆 | 80,400 | ○ |
| 紅茶ティーバッグ | 112,200 | ○ |
| 緑茶ボトル | 44,130 | × |
→ 2

### 3. なぜ [売上金額] が「その商品の売上」になるのか
FILTER は商品名を1つずつ見ていきます（行コンテキスト）。そこで **メジャーを書くと、自動的に「その行の商品名」という条件に変換されて** 計算されます。これを **コンテキスト遷移** と呼びます。「メジャーは、今見ている行の値で絞り込んでから計算してくれる」と覚えておきましょう。

### 4. CALCULATE と組み合わせる
```dax
まとめ買い売上 = CALCULATE([売上金額], FILTER(売上, 売上[数量] >= 10))
```
FILTER で選んだ行（数量10以上の注文）だけで売上金額を計算します。この例は `売上[数量] >= 10` と単純に書いても同じ結果になります。

### 5. 使い分け
| 条件 | 書き方 |
|---|---|
| 列 = 値 の単純な条件 | CALCULATE([…], 商品[カテゴリ] = "菓子") |
| メジャーや計算結果を条件にする | FILTER(VALUES(列), [メジャー] >= …) |
大きなファクト表（売上）全体を FILTER するより、**VALUES(列) のような小さい表を FILTER** するほうが速く、意図も明確です。

@pitfalls
- **FILTER の1つ目に列を渡す** `FILTER(商品[商品名], …)` → テーブルが必要。VALUES(商品[商品名]) や ALL(…)
- **FILTER の結果をそのまま表示** → 表なので数値にならない。COUNTROWS などで包む
- **VALUES と ALL の違い** VALUES は今見えている値（行の条件が効く）、ALL は全部
- **CALCULATE の条件に直接メジャー** → エラー。FILTER の中に書く

@steps bi9a
1. 「金額5000以上の注文」は FILTER(売上, 売上[金額] >= 5000) で取り出せる
2. それが何件かを数えるので COUNTROWS(…) で包む
3. 確定して、カテゴリ×年 の件数を確認して採点

@steps bi9b
1. 数えたいのは「商品」なので、商品名の一覧 VALUES(商品[商品名]) を使う
2. FILTER の条件は [売上金額] >= 50000（メジャーが各商品の売上になる）
3. COUNTROWS で残った商品の数を数えて確定・採点

@steps bi9c
1. FILTER(売上, 売上[数量] >= 10) で「数量10以上の注文」の表を作る
2. それを CALCULATE([売上金額], …) の条件に渡す
3. 確定して採点

@@lesson bi10
@image
**RELATEDTABLE** は RELATED の逆向きです。

- RELATED：売上の1行 → その行の **商品の情報** を1つ取る（多 → 1）
- RELATEDTABLE：商品の1行 → その商品の **売上の行をぜんぶ** 取る（1 → 多）

商品表に「この商品は何個売れたか」、顧客表に「この人は何回買ったか」のような **集計結果の列** を作りたいときに使います。

また今日は、DAX でつまずく人が最も多い **「計算列で SUM を書くと全部同じ値になる」** 問題と、その解決法（CALCULATE）を扱います。

@detail
### 1. RELATEDTABLE で関連する行を取る
商品テーブルに計算列を作ります。
```dax
販売数量 = SUMX(RELATEDTABLE(売上), 売上[数量])
```
| 商品ID | 商品名 | RELATEDTABLE(売上) で取れる行 | 販売数量 |
|---|---|---|---|
| P01 | コーヒー豆 | P01 の注文だけ | 55 |
| P02 | 紅茶ティーバッグ | P02 の注文だけ | 189 |
1. 商品テーブルを1行ずつ計算（計算列なので行コンテキストがある）
2. RELATEDTABLE(売上) が、その商品の売上の行だけの表を返す
3. SUMX でその表の数量を合計

### 2. 件数なら COUNTROWS
```dax
購入回数 = COUNTROWS(RELATEDTABLE(売上))     // 顧客テーブルの計算列
```

### 3. つまずきポイント：計算列で SUM を書くと…
商品テーブルに `= SUM(売上[数量])` という計算列を作ると：
| 商品名 | SUM(売上[数量]) |
|---|---|
| コーヒー豆 | 1,821 |
| 紅茶ティーバッグ | 1,821 |
| … | 1,821 |
**全部同じ値（全体の合計）** になります。
- 計算列には「今どの行か」（行コンテキスト）はある
- でも「その商品で絞る」という条件（フィルターコンテキスト）は **ない**
- SUM は条件で絞られた行を合計する関数なので、条件がなければ全部を合計してしまう

### 4. CALCULATE で包むと解決（コンテキスト遷移）
```dax
販売数量2 = CALCULATE(SUM(売上[数量]))
```
| 商品名 | CALCULATE(SUM(売上[数量])) |
|---|---|
| コーヒー豆 | 55 |
| 紅茶ティーバッグ | 189 |
CALCULATE には **「今の行」を「条件」に変換する** 働きがあります（コンテキスト遷移）。コーヒー豆の行では「商品＝コーヒー豆」という条件に変わり、その条件が売上に流れて、コーヒー豆の数量だけが合計されます。

> メジャーを参照（[数量合計] など）したときも、自動で CALCULATE で包まれるので同じ効果があります（第9回の FILTER の中のメジャーと同じしくみ）。

### 5. 顧客ランク（計算列で分類）
```dax
ランク = IF(CALCULATE(SUM(売上[金額])) >= 80000, "A", "B")
```
顧客テーブルに作ると、顧客ごとの売上で A/B に分けられます。この列はスライサーやマトリックスの行に使えます（列なので）。

@pitfalls
- **計算列で SUM だけ** → 全行が同じ値。CALCULATE で包むか RELATEDTABLE を使う
- **RELATED と RELATEDTABLE の向き** 多→1 は RELATED（値を1つ）、1→多 は RELATEDTABLE（表）
- **RELATEDTABLE の結果をそのまま表示** → 表なので、COUNTROWS や SUMX で数値にする
- **計算列の値は更新時に決まる** レポートのスライサーでは変わらない（期間で変わる指標はメジャーで）

@steps bi10a
1. 商品テーブルの計算列なので、「その商品の売上の行」は RELATEDTABLE(売上)
2. その表の数量を合計する → SUMX(RELATEDTABLE(売上), 売上[数量])
3. 「列を追加」してテーブルタブで確認して採点

@steps bi10b
1. 顧客テーブルの計算列。「その顧客の売上の行」は RELATEDTABLE(売上)
2. 行数を数える → COUNTROWS(…)
3. 「列を追加」して採点

@steps bi10c
1. その顧客の売上金額は CALCULATE(SUM(売上[金額]))（CALCULATE がないと全員同じ値になる）
2. IF(その金額 >= 80000, "A", "B")
3. 「列を追加」してテーブルタブで A と B が混ざっているか確認して採点

**タイムインテリジェンス**は、「年初からの累計」「前年の同じ時期」のような **時間の比較** を簡単に書くための関数群です。

経営会議でよく聞かれる「今年は前年と比べてどう？」「年度が始まってから累計でいくら？」── Excel では行をずらして参照したり、SUMIFS の日付条件を毎月書き換えたりしていた計算が、1行の式で、どの月の行でも自動で正しく計算されます。

前提は、**連続した日付を持つ日付テーブル（カレンダー）** があることです。

@detail
### 1. 日付テーブルが必要な理由
売上[日付] には、注文がなかった日は存在しません。「1年前の同じ期間」を計算するには、**1日も欠けていないカレンダー** が必要です。このアプリのモデルでは カレンダー（2025/1/1〜2026/6/30）が売上[日付] とつながっています。
> タイムインテリジェンス関数には必ず **カレンダー[日付]** を渡します（売上[日付] ではなく）。

### 2. 年累計（YTD = Year To Date）
```dax
売上YTD = TOTALYTD([売上金額], カレンダー[日付])
```
| 年月 | 売上金額 | 売上YTD | 計算 |
|---|---|---|---|
| 2025-01 | 35,040 | 35,040 | 1月 |
| 2025-02 | 16,304 | 51,344 | 1〜2月 |
| 2025-03 | 28,038 | 79,382 | 1〜3月 |
| … | | | |
| 2026-01 | 39,255 | 39,255 | 年が変わるとリセット |
各行で「その年の1月1日から、その行の最後の日まで」の売上を計算します。

### 3. 4月始まりの年度累計
```dax
売上FYTD = TOTALYTD([売上金額], カレンダー[日付], "3/31")
```
3つ目に **年度末の日付** を書くと、年度の始まり（4/1）から累計します。
| 年月 | 売上FYTD |
|---|---|
| 2025-03 | 79,382（2024年度の累計：1〜3月分） |
| 2025-04 | 41,880（新年度でリセット） |
| 2025-05 | 72,710 |

### 4. 前年同期
```dax
前年売上 = CALCULATE([売上金額], SAMEPERIODLASTYEAR(カレンダー[日付]))
```
| 年月 | 売上金額 | 前年売上 |
|---|---|---|
| 2025-01 | 35,040 | （空白：2024年のデータがない） |
| 2026-01 | 39,255 | 35,040 |
| 2026-02 | 44,928 | 16,304 |
2026-01 の行では、SAMEPERIODLASTYEAR が「2025年1月の日付」を返し、CALCULATE がその期間で売上を計算します。

### 5. 前年比
```dax
前年比 = DIVIDE([売上金額] - [前年売上], [前年売上])
```
| 年月 | 前年比 |
|---|---|
| 2025-01 | （空白） |
| 2026-01 | 12.0% |
| 2026-03 | -6.2% |
前年売上が空白の月は、DIVIDE のおかげで前年比も空白になり、おかしな数字が出ません。

@pitfalls
- **売上[日付] を渡す** → 欠けている日があり正しく計算できない。カレンダー[日付]
- **年度末の書き方** "3/31"（文字列）。4/1 ではなく「年度の最後の日」
- **前年比を / で計算** → 前年がない月に ∞。DIVIDE
- **合計行の値** YTD の合計行は「最後の日までの累計」になる（全期間の合計とは限らない）

@steps bi11a
1. 年累計は TOTALYTD(式, 日付列)
2. 式は [売上金額]、日付列は カレンダー[日付]
3. 確定して、1月から増えていき翌年1月でリセットされることを確認して採点

@steps bi11b
1. bi11a と同じ TOTALYTD に、3つ目の引数として年度末 "3/31" を足す
2. 確定して、4月でリセットされることを確認して採点

@steps bi11c
1. 「前年の同じ期間」の日付は SAMEPERIODLASTYEAR(カレンダー[日付])
2. それを CALCULATE([売上金額], …) の条件に渡す
3. 確定して、2026年の行に2025年の値が出ることを確認して採点

@steps bi11d
1. 既にある [売上金額] と [前年売上] を使う
2. 前年比 ＝ (売上金額 − 前年売上) ÷ 前年売上
3. 割り算は DIVIDE。分子は [売上金額] - [前年売上]、分母は [前年売上]
4. 確定して、2025年の行が空白になることを確認して採点

@@lesson bi12
@image
前回の「前年」に続いて、今回は **「前月」** と **「直近3か月」** です。

- 前月比：月次の会議で「先月より増えた？減った？」
- 移動平均：月ごとの売上はデコボコするので、**直近3か月の平均** で均すと、上がっているのか下がっているのか傾向が見えやすくなります（天気予報の「平年並み」のような見方）

どちらも、「今の行の期間」を **ずらす・広げる** 関数で作ります。

@detail
### 1. DATEADD ― 期間をずらす
```dax
前月売上 = CALCULATE([売上金額], DATEADD(カレンダー[日付], -1, MONTH))
```
| 部分 | 意味 |
|---|---|
| カレンダー[日付] | 今の行の日付（例：2025年2月の28日分） |
| -1 | 1つ前へ |
| MONTH | 月単位で（DAY / MONTH / QUARTER / YEAR） |

| 年月 | 売上金額 | 前月売上 |
|---|---|---|
| 2025-01 | 35,040 | （空白） |
| 2025-02 | 16,304 | 35,040 |
| 2025-03 | 28,038 | 16,304 |
`DATEADD(…, -12, MONTH)` や `DATEADD(…, -1, YEAR)` は前年同期と同じ意味になります。

### 2. 前月比
```dax
前月比 = DIVIDE([売上金額] - [前月売上], [前月売上])
```
| 年月 | 前月比 |
|---|---|
| 2025-02 | -53.5% |
| 2025-03 | 72.0% |
| 2025-04 | 49.4% |

### 3. DATESINPERIOD ― 期間を広げる（直近3か月）
```dax
直近3か月売上 = CALCULATE([売上金額], DATESINPERIOD(カレンダー[日付], MAX(カレンダー[日付]), -3, MONTH))
```
| 部分 | 2025-04 の行では |
|---|---|
| MAX(カレンダー[日付]) | その行の最後の日 → 2025/4/30 |
| -3, MONTH | そこから3か月さかのぼる |
| 結果の期間 | 2025/2/1 〜 2025/4/30 |

### 4. 3で割って移動平均
```dax
3か月移動平均 = CALCULATE([売上金額], DATESINPERIOD(カレンダー[日付], MAX(カレンダー[日付]), -3, MONTH)) / 3
```
| 年月 | 売上金額 | 3か月移動平均 |
|---|---|---|
| 2025-01 | 35,040 | 11,680（データは1か月分だけ ÷3） |
| 2025-03 | 28,038 | 26,461（1〜3月の平均） |
| 2025-04 | 41,880 | 28,741（2〜4月の平均） |
> 最初の2か月は、さかのぼる期間にデータがないので小さめになります。気になる場合は、データの月数で割る工夫もできます。

### 5. グラフで見ると
折れ線グラフに「売上金額」と「3か月移動平均」を重ねると、デコボコの実績と、なめらかな傾向線が並び、傾向が一目で分かります。

@pitfalls
- **DATEADD の単位** MONTH などは " " で囲まない（そのまま書く）
- **マイナスの向き** 前月は -1、翌月は +1
- **MAX(売上[日付]) と書く** → 注文のない日が最終日にならない。カレンダー[日付]
- **3で割るのを / で** 3 は0にならないので / でOK（分母がメジャーなら DIVIDE）

@steps bi12a
1. 1か月前の期間は DATEADD(カレンダー[日付], -1, MONTH)
2. それを CALCULATE([売上金額], …) の条件に渡す
3. 確定して、各行に前の月の売上が出ることを確認して採点

@steps bi12b
1. 既にある [売上金額] と [前月売上] を使う
2. DIVIDE(売上金額 − 前月売上, 前月売上)
3. 確定して採点

@steps bi12c
1. 直近3か月の期間は DATESINPERIOD(カレンダー[日付], MAX(カレンダー[日付]), -3, MONTH)
2. CALCULATE([売上金額], その期間) で3か月の合計
3. 全体を / 3 で平均にして確定・採点

@@lesson bi13
@image
レポートを見やすくするための **「条件で表示を変える」** テクニックです。

- 売上に応じて **A / B / C の評価** を付ける
- **合計行には出したくない** 値（平均単価や順位）を空白にする
- 選んでいるカテゴリ名を **見出しに表示** する

どれも「今どんな条件で見られているか」を DAX で判断して、出す値を切り替えます。

@detail
### 1. SWITCH(TRUE(), …) ― 上から順に判定
```dax
売上評価 = SWITCH(TRUE(),
    [売上金額] >= 50000, "A",
    [売上金額] >= 30000, "B",
    "C"
)
```
| 商品 | 売上金額 | 判定の流れ | 評価 |
|---|---|---|---|
| クッキー | 97,470 | 5万以上 → はい | A |
| チョコレート | 44,010 | 5万以上 → いいえ、3万以上 → はい | B |
| ファイル | 28,000 | どちらも いいえ | C |
「最初に TRUE になった条件の結果」を返します。IF を何重にも入れ子にするより読みやすく書けます。最後の1つ（"C"）は、どれにも当てはまらないときの値です。

### 2. HASONEVALUE ― 1つに絞られているか
| 行 | 商品[カテゴリ] の見えている値 | HASONEVALUE(商品[カテゴリ]) |
|---|---|---|
| ドリンク | ドリンク だけ | TRUE |
| 菓子 | 菓子 だけ | TRUE |
| 合計 | 4つ全部 | **FALSE** |
合計行だけ FALSE になるので、これで合計行を見分けられます。
```dax
カテゴリ別売上 = IF(HASONEVALUE(商品[カテゴリ]), [売上金額])
```
IF の3つ目（偽のとき）を省略すると **空白** になり、合計行には何も表示されません。

### 3. SELECTEDVALUE ― 選ばれている値を取り出す
```dax
見出し = "カテゴリ: " & SELECTEDVALUE(商品[カテゴリ], "すべて")
```
| 行 | 見出し |
|---|---|
| ドリンク | カテゴリ: ドリンク |
| 菓子 | カテゴリ: 菓子 |
| 合計 | カテゴリ: すべて |
- 値が1つに絞られていればその値、そうでなければ2つ目の引数（"すべて"）
- `&` で文字をつなげる（Excel と同じ）
- カードのビジュアルに置いたり、グラフのタイトルに設定したりすると、スライサーの選択に応じて変わる見出しになる

### 4. ISINSCOPE（参考）
行に「カテゴリ → 商品名」の階層があるとき、「今は商品名の行か？」を判定します。階層ごとに表示を変えたいときに使います。

@pitfalls
- **SWITCH の条件の順番** 厳しい条件（5万以上）を先に。3万以上を先に書くと、5万以上も B になる
- **SWITCH(TRUE(), …) の TRUE() を忘れる** → 条件を値として比べてしまい、正しく分岐しない
- **IF の3つ目に 0 を書く** → 合計行に 0 が表示される。空白にしたいなら省略
- **SELECTEDVALUE に代わりの値を書かない** → 合計行で空白になり「カテゴリ: 」だけになる

@steps bi13a
1. 判定は3段階：5万以上 → "A"、3万以上 → "B"、それ以外 → "C"

@@lesson bi14
@image
「売上ランキング」「トップ3」は、レポートで最も目を引く情報です。

- **RANKX**：順位を付ける（1位、2位、…）
- **TOPN**：上位 N 件だけを取り出す

どちらも、**比べる相手全員の一覧** を用意してから、その中で並べるのがポイントです。ここで ALL が再び活躍します。

@detail
### 1. RANKX の形
```dax
売上順位 = RANKX(ALL(商品[商品名]), [売上金額])
```
| 部分 | 意味 |
|---|---|
| ALL(商品[商品名]) | 比べる相手：**全商品**の一覧 |
| [売上金額] | 何で比べるか |

### 2. ALL がないとどうなる？
`RANKX(VALUES(商品[商品名]), [売上金額])` と書くと、全行が **1位** になります。
| 行 | VALUES(商品[商品名]) の中身 | 順位 |
|---|---|---|
| クッキー | クッキー だけ | 1（1人の中で1位） |
| コーヒー豆 | コーヒー豆 だけ | 1 |
各行では行の条件で商品が1つに絞られているので、比べる相手が自分しかいないのです。ALL で条件を外して「全商品の中で」比べる必要があります。

### 3. 順位の結果
| 商品名 | 売上金額 | 売上順位 |
|---|---|---|
| 紅茶ティーバッグ | 112,200 | 1 |
| クッキー | 97,470 | 2 |
| コーヒー豆 | 80,400 | 3 |
- 4つ目の引数に ASC を書くと小さい順（少ないほど1位）
- 5つ目に DENSE を書くと、同順位の後の番号を詰める（1, 1, 2…）

### 4. 合計行の順位を消す
合計行の順位は意味がないので、第13回の HASONEVALUE で空白にします。
```dax
顧客順位 = IF(HASONEVALUE(顧客[顧客名]), RANKX(ALL(顧客[顧客名]), [売上金額]))
```

### 5. TOPN ― 上位 N 件の表
```dax
TOPN(3, ALL(商品[商品名]), [売上金額])
```
「全商品を売上金額の大きい順に並べて、上から3つ」の **表** を返します。表なので、CALCULATE の条件に渡して使います。
```dax
上位3商品売上 = CALCULATE([売上金額], TOPN(3, ALL(商品[商品名]), [売上金額]))
```
| 年 | 上位3商品売上 |
|---|---|
| 2025 | 179,550 |
| 2026 | 116,292 |
2025年の列では、**2025年の売上で** 上位3商品が選ばれ、その3商品の2025年の売上が合計されます（年によって上位の商品が変わってもよい）。

@pitfalls
- **RANKX で ALL を忘れる** → 全部1位
- **TOPN の結果をそのまま表示** → 表なので、CALCULATE や COUNTROWS と組み合わせる
- **同順位の扱い** 既定は「1, 1, 3」。詰めたいなら DENSE
- **合計行の順位** 1位などと表示されて紛らわしい → HASONEVALUE で空白に

@steps bi14a
1. 比べる相手は全商品 → ALL(商品[商品名])
2. 比べるものは [売上金額]
3. RANKX(相手, 比べるもの) で確定し、順位がバラバラに付くことを確認して採点

@steps bi14b
1. 上位3商品の一覧は TOPN(3, ALL(商品[商品名]), [売上金額])
2. それを CALCULATE([売上金額], …) の条件に渡す
3. 確定して、年ごとに値が出ることを確認して採点

@steps bi14c
1. 順位は RANKX(ALL(顧客[顧客名]), [売上金額])
2. 合計行を空白にするため、IF(HASONEVALUE(顧客[顧客名]), 順位の式) で包む（3つ目は省略）
3. 確定して、合計行が空白になることを確認して採点

@@lesson bi15
@image
ここまでで、データモデルとメジャーという **「レポートのエンジン」** ができました。最後は、それを **伝わる形に見せて、チームで使う** 段階です。

どんなに正しい数字でも、グラフの種類が合っていなかったり、見る人が欲しい切り口で絞れなかったりすると伝わりません。また、Power BI の本当の価値は **Service（Web）に発行して、毎日自動で最新になるレポートをみんなが見られる** ことにあります。

@detail
### 1. 何を見せたいかでグラフを選ぶ
| 見せたいこと | おすすめ | 避けたい |
|---|---|---|
| 月ごとの推移 | 折れ線・縦棒 | 円グラフ |
| 項目の比較・ランキング | 横棒（並べ替えて） | 項目が多い円グラフ |
| 全体に占める割合 | 積み上げ棒、項目が少なければ円 | 10項目以上の円 |
| 最重要の1つの数字 | カード（KPI） | 表 |
| 詳細の数字 | マトリックス・テーブル | 大量のグラフ |

### 2. ダッシュボードの典型的なレイアウト
```
┌─────────┬─────────┬─────────┐
│ 売上金額   │ 粗利率    │ 前年比     │ ← カード（結論を先に）
├─────────┴─────────┴─────────┤
│ 月別の売上（折れ線）           │ ← 推移
├───────────────┬─────────┤
│ 商品別の売上（横棒）    │ スライサー │ ← 内訳と絞り込み
└───────────────┴─────────┘
```
上に結論（カード）、中に推移、下に内訳。見る人の目線は左上から右下へ動きます。

### 3. 操作性
| 機能 | 何ができるか |
|---|---|
| 相互作用 | グラフの棒をクリックすると、他のグラフもその条件で絞られる |
| スライサー | 年・地域などをボタンで選んで絞り込む |
| ドリルダウン | 年 → 四半期 → 月 と細かくしていく |
| ドリルスルー | 商品をクリックして、その商品の詳細ページへ移動 |
| ツールヒント | マウスを乗せると小さなグラフを表示 |

### 4. 発行と自動更新
1. Power BI Desktop で **ホーム → 発行** → ワークスペースを選ぶ
2. ブラウザ（Power BI Service）やスマホの Power BI アプリで見られる
3. **スケジュール更新**：毎朝など決まった時刻にデータを読み直す
   - クラウドのデータ（SharePoint、OneDrive など）はそのまま更新できる
   - 社内のファイルサーバーや社内データベースには **オンプレミス データ ゲートウェイ** が必要
4. 共有：ワークスペースへの招待や「アプリ」として配布（閲覧する人にもライセンスが必要な場合が多い。会社の契約を確認）

### 5. 行レベル セキュリティ（RLS）
「営業担当は自分の地域のデータだけ見られる」ようにするしくみ。
- モデリング → **ロールの管理** で、ロール（例：東京担当）と条件（`顧客[地域] = "東京"`）を作る
- Service で、ユーザーをロールに割り当てる
- 自分のメールアドレスで絞る `USERPRINCIPALNAME()` を使えば、1つのロールで全員分に対応できる
スライサーは見る人が自由に外せるので、**見せてはいけないデータの制限には使えません**。必ず RLS を使います。

@pitfalls
- **グラフの詰め込みすぎ** 1ページに伝えたいことは1〜2つ
- **円グラフに項目を詰め込む** → 比較できない。横棒にして並べ替え
- **社内データなのにゲートウェイを用意していない** → Service で更新が失敗する
- **スライサーで見せる範囲を制限する** → 利用者が外せる。権限の制御は RLS
